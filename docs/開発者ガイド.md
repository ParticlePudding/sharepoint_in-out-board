プログラムの構成、ローカルでの動かし方、主な処理の流れ、よくある改修の手順をまとめています。

## 1. 技術構成

| 項目 | 内容 |
|---|---|
| 言語 | 素の HTML / CSS / JavaScript（ES2020 程度）。ビルド不要、フレームワークなし |
| データ | SharePoint Online のリスト（REST API `/_api/web/lists/...`） |
| 認証 | ブラウザの SharePoint セッション（`credentials: "same-origin"`）。更新系は FormDigest を付与 |
| 外部依存 | なし（CDN 不使用）。アイコンは Lucide の SVG を `icons.js` に埋め込み |
| 対応ブラウザ | Edge / Chrome / Safari（iOS 含む）の最新版 |
| 自動テスト | なし（手動確認。6章） |

## 3. ローカルで動かす

### 起動
任意の静的サーバーで、`index.html` のあるフォルダを配信します。

```bash
python -m http.server 8765 --bind 127.0.0.1
```

`http://localhost:8765/?mock=1` を開きます。

### モック動作（テストデータ）
URL に **`?mock=1`** があるときだけ、SharePoint に接続せず `js/sample-data.js` のデータで動きます（`CONFIG.USE_MOCK_DATA`）。
`?mock=1` がなければ、`localhost` や `file://` で開いても本物と同じ通信をします（SharePoint、または次のモックサーバー）。

モックでは書き込みもメモリ上だけで、再読み込みすると元に戻ります。
テストデータで動いている間は、画面の左下に「テストデータで動作中（保存されません）」と表示します（`app.showMockBadge`）。

### 通信の遅さ・失敗を再現（モック時のみ）

| パラメータ | 内容 |
|---|---|
| `?mockdelay=2000` | 取得・保存に毎回2秒かかる |
| `?mockfail=1` | 保存が必ず失敗する（再送→失敗通知→取り直しの確認用） |

例：`http://localhost:8765/?mock=1&mockdelay=2000`

### モックサーバー（本物と同じ通信で試す・複数端末で保存を共有する）
別プロジェクトの **SharePoint モックサーバー**（`動静表` と同じ階層の `SharePointモックサーバー` フォルダ）を使います。
SharePoint REST API の一部（取得・追加・更新・削除・FormDigest・ETag）をまねる Python のサーバーで、座席表と会議室予約の両方を1つのサーバーで配信します。

```bash
cd ../SharePointモックサーバー     # 置いた場所に合わせる
python mockserver.py              # http://localhost:8000/ を開く
python mockserver.py --reset      # データを消してサンプルを入れ直す
```

- 座席表は `http://localhost:8000/SiteAssets/seatmap/index.html` で開きます（`?mock=1` は付けない）。
- モックサーバーは既定で、この PC（127.0.0.1）からの接続だけを受け付けます。
- 初回は `js/sample-data.js` の内容が入ります。データはモックサーバーのフォルダの SQLite ファイルに保存されます。
- 詳しくはモックサーバーの README を参照してください。

### 実リストにテストデータを入れる
`index.html` に一時的に `<script src="tools/seed.js"></script>` を足し、SharePoint 上で開いてコンソールで `await spSeeder.run()` を実行します。終わったら行を戻してください。

## 4. 主な処理の流れ

### 4-1. 起動（`app.init`）
1. `detectSignageMode()`（`?signage=1`）
2. `buildStatusUi()`：`CONFIG.STATUS_VIEW` からステータスボタン・選択肢を生成
3. `SaveQueue.init()`
4. 各画面の `init()`（1つの失敗で全体が止まらないよう個別に try）
5. `initModalA11y()`（フォーカス移動・Tab 循環）、`initOverflowTooltips()`
6. `refreshAll()` → `handleUrlParams()` → `startAutoRefresh()`

### 4-2. データ取得（`app.runRefresh`）
- データは `app.items`（社員名簿の配列）に1か所で持ちます。各画面はここから描画します。
- **全件**（`getAllFull`）：起動時・更新ボタン・日付変更時・サイネージの15分ごと。全列を取得し `app.items` を置き換え。
- **軽量**（`getFrequentOnly`）：1分ごと。`Id, Status, Remarks, NextSchedule, Seat` だけ取得して上書き（席替えも1分以内に反映）。
- 取得は直列化されます。実行中の要求は1つにまとめて、終了後に再実行します。
- ステータス画面・設定画面・グループ設定を開いている間、一括モード中、タブが非表示の間はポーリングしません（`canBackgroundRefresh`）。タブに戻ったとき、前回から1分以上経っていればすぐ取得します。
- 取得後に `SaveQueue.overlay()` で未送信の変更を重ね直します（表示が一瞬戻るのを防ぐ）。
- SharePoint は `Id` で500件ずつページングして取得します（501件目以降の欠落防止）。

### 4-3. 書き込み（`SaveQueue`）
利用者の操作による書き込みは、すべて `SaveQueue.enqueue(id, fields)` を通します。

```
操作 ─▶ enqueue ─▶ app.items にすぐ反映（楽観的更新）─▶ 画面を再描画
            │
            ├─ ステータス画面で開いている人（holdId）… 画面を閉じるまで送らず、変更をまとめる
            │                                          （最大 CONFIG.SAVE_HOLD_MAX_MS）
            └─ それ以外 ……………………………………………… すぐ送信（同時 WRITE_CONCURRENCY 件まで）

送信（spApi.update = MERGE）
   成功 → 完了
   失敗 → 2秒後・4秒後に再送（SAVE_RETRY_MAX）→ それでも失敗：通知して refreshAll（サーバーの値に戻す）
   404  → 「削除済み」と通知
```

- 同じ人への変更は1つのオブジェクトにマージされ、1回の MERGE で送ります。
- 送信中に同じ人の変更が来たら、送信完了後に続けて送ります（順序保証＝最後の操作が勝つ）。
- `beforeunload` で未送信があれば `keepalive` 付きで送信し、ブラウザの確認を出します。`visibilitychange`（非表示）でも即送信します。
- 送信が0.6秒を超えたときだけ `#syncIndicator`（送信中…）を出します。

**対象外（結果を待つもの）**

| 処理 | 理由 |
|---|---|
| `SettingsModal` の追加・編集・削除 | 入力チェック・作成後の Id 取得・権限エラーの即時表示が必要 |
| `StatsScreen.saveGroupsToServer` | ETag による楽観ロック（412 で競合検知） |
| `app.processDueSchedules`（サイネージ） | 反映直前の再取得で二重反映を防ぐため |

### 4-4. ステータス画面の保存ルール（`StatusModal`）
- 画面を閉じるのはステータスボタンだけ（`submit({ close: true })`）。
- 備考の保存・削除、定型文、予定予約は保存しても閉じません。
- ステータスボタンを押したとき、未保存の備考（`isNoteDirty`）と予定予約（`isScheduleDirty`）も同じ送信に含めます。
- ×・背景・Esc は `requestClose()`。未保存があれば `confirm` を出します。

### 4-5. 予定予約の反映（`app.processDueSchedules`、サイネージのみ）
1. 全件取得・軽量取得のたびに（＝1分ごと）、予約日時（`date`+`time`）が今以前の人を抽出。
2. 0〜20秒のランダム待機（複数サイネージの衝突回避）。
3. 1件ずつ最新の `NextSchedule` を取り直し、まだ残っていれば反映。
   - 当日の予約：`Status`・`Remarks` を予約の値にし、`NextSchedule` を空に。
   - 前日以前の予約：`NextSchedule` を空にするだけ。
4. 同じ値の上書きなので、万一重なっても結果は同じ（冪等）。

## 5. よくある改修

### 5-1. フロア・席を変える（`config.js` の `FLOORS`）
```js
{
  id: "2F",                    // フロアID（席番号の頭と揃えると分かりやすい）
  name: "2F 営業部",            // フロア切替ボタンの表示
  image: "img/floor/2f.svg",   // 見取り図（index.html からの相対パス。png・jpg・svg）
  width: 1920, height: 1080,   // 見取り図の座標系（省略時 MAP_W / MAP_H）
  seats: {
    "2F-A01": { left: 80, top: 90, size: "standard" },   // 150×80
    "2F-A02": { left: 80, top: 200, size: "vertical" },  // 86×150
    "2F-A03": { left: 300, top: 90, size: "free", width: 160, height: 90 }
  }
}
```
- `left` / `top` は見取り図の左上からの位置（px、`width`×`height` の座標系）。見取り図の画像も同じ縦横比で作ってください。
- 席番号は全フロアで重複しないこと（`ALL_SEATS_MAP` で逆引きするため）。
- 席番号は大文字で書くこと（入力側は NFKC＋大文字化して照合します）。

### 5-2. ステータスを追加・変更する
1. `config.js` の `STATUS` に定数を追加。
2. `CONFIG.STATUS_VIEW` に表示設定を追加。**キーの並び順がボタン・選択肢の並び順**になります。
   - `cls`：座席カードの色クラス（`seat-green` など）
   - `pill`：丸・バッジの色（`green` `blue` `yellow` `red` `white`）
   - `label`：座席カードの文字、`menuLabel`：ボタン・選択肢の文字
3. `CONFIG.STATUS_ORDER` に並び替え順を追加。
4. 新しい色を使う場合は `css/styles.css` に `.seat-xxx` `.status-pill.xxx` `.status-dot.dot-xxx` `.status-filter-check.checked.pill-xxx` を追加。
5. `index.html` の人数表の見出し（`<th>`）と、`view-stats.js` の `render()`（集計の `makeBucket`・`switch`・列の配列・合計・空表示の `colSpan`）に列を追加。
   - 例：「在宅」は `STATUS.HOME`・オレンジ（`seat-yellow` / `yellow`。出張と同じ）・並び順5で、人数表では出張の右に列があります。
   - ステータス画面のボタンは2列です。「未入力」は、ステータスの数が偶数なら最後の行に横いっぱい、奇数なら最後の空いたマスに自動で入ります。
6. 既存データの値を変える場合は、社員名簿の `Status` と `NextSchedule` 内の `status` も書き換えが必要です。

### 5-3. 列を追加する
1. SharePoint のリストに列を追加（内部名は英字で）。
2. 定周期で更新したい列なら `api.js` の `getFrequentOnly` の `$select` に追加。
3. 書き込むときは `SaveQueue.enqueue(id, { 列名: 値 })`。

### 5-4. アイコンを追加する
1. [Lucide](https://lucide.dev/) から SVG を取得。
2. `icons.js` の `Icons.paths` に `<svg>` の中身（`<path>` など）を追加。
3. HTML では `<i class="ic" data-icon="名前"></i>`、JS では `Icons.setLabel(el, "名前", "文字")`。
4. `THIRD_PARTY_NOTICES.txt` の「使用アイコン」に追記。

### 5-5. スマホ判定を変える
`CONFIG.PHONE_MEDIA_QUERY` と、`css/styles.css` 末尾の `@media` の条件を**必ず同じ**にしてください（JS と CSS で判定がずれると表示が崩れます）。

## 7. コーディング上の決まり

- **DOM への文字の挿入は `textContent`**。`innerHTML` は `icons.js` の固定SVG以外で使わない（XSS対策）。
- セレクタに値を埋め込むときは `CSS.escape()`。
- 「はい／いいえ」以外の選択肢が要る確認は `app.choose({ title, message, choices })`（Promise で選んだ `value`、やめたら `null`）。2択は従来どおり `confirm()`。
- localStorage は `app.loadCache()` / `app.saveCache()` を使い、読んだ値は許可リストで検証する（`LIST_SORT_KEYS` など）。
- ステータスの表示は `getStatusView()` / `isValidStatus()` を通す（不正値は「未入力」扱い）。
- 席番号は `app.parseSeats()`、予約は `app.parseSchedule()` を通す（表記ゆれ・不正JSON対策、結果はキャッシュ）。
- 日付は `DateUtils`（`CONFIG.TIMEZONE`＝日本時間）。端末の時計のタイムゾーンに依存しない。
- 書き込みは `SaveQueue` 経由（4-3の対象外を除く）。
- スマホ判定は `app.isPhone()`。
- コメントは日本語で「なぜそうしているか」を書く。

## 8. 既知の制約

- 同じ人を複数人が同時に編集した場合は、後から保存したほうが残ります（`IF-Match: *`）。
- 社員の追加・削除が他の端末に反映されるのは全件取得時（起動時・更新ボタン・日付変更時）。
- ステータス画面を開いたままの間の変更は、閉じるまで（最大20秒）他の端末に届きません。
- 予約の反映はサイネージ頼み。サイネージが動いていない日は反映されません。
- 「自分」は端末の localStorage に Id を覚えるだけで、本人確認ではありません。
